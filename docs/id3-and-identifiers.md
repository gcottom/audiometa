# ID3, identifiers, and audio analysis conventions

This research describes the storage choices available to AudioMeta. Adapter tests and independent tooling establish which choices the implementation supports.

## ID3 versions

| Version | Storage and text | Recommended compatibility policy |
| --- | --- | --- |
| ID3v1 and v1.1 | Optional 128-byte trailer. Title, artist, album, year, comment, and genre byte. v1.1 reuses two comment bytes for the separator and track number. | Read the limited trailer as a lower-precedence source. Preserve its bytes when unrelated fields change. Write extended values to a leading ID3v2 tag. Clearing a canonical field must prevent the old trailer value from resurfacing. Character encoding, truncation, fixed size, and genre numbering limit faithful v1 writes. |
| ID3v2.2 | Leading tag with three-character frame IDs and 24-bit frame lengths. Latin-1 and Unicode with byte order marker. Common equivalents include TT2, TP1, TAL, TRK, TPA, TXX, WXX, COM, ULT, SLT, PIC, and UFI. | Use version-specific decoding. Keep opaque three-character frames in their original version. Treat tag-wide compression and unsupported flags as preservation constraints. PIC encodes a three-character image format in place of the MIME string used by APIC. |
| ID3v2.3 | Four-character frame IDs, 32-bit big-endian frame sizes, tag-wide unsynchronization, and Latin-1 or UTF-16 with byte order marker. | Keep the original version where safe. Slash separators have specific meanings in some frames and are ambiguous for arbitrary text. Use the AudioMeta fallback or an explicit error when a native write would lose value boundaries. TYER, TDAT, and TIME are separate and cannot represent arbitrary reduced precision. |
| ID3v2.4 | Four-character frame IDs, synchsafe frame sizes, optional footer, per-frame unsynchronization, and additional UTF-8 and UTF-16BE support. Text information frames can represent multiple strings using encoding-specific null termination. Dates use reduced-precision UTC timestamps. | Prefer v2.4 for a new tag. Keep input frame order, flags, and opaque bytes where possible. Confirm the actual encoding on read. Use the same version for updates and preserve permitted extended headers, padding, and footers or explicitly reject a rewrite that cannot preserve them. |

The ID3 project describes the ID3v2 documents as informal standards. The compatibility registry uses **Native** for frames defined by the relevant ID3 format specification and **Conventional** for usage established outside that specification. [ID3v1 and v1.1](https://id3.org/ID3v1), [ID3v2.2](https://id3.org/id3v2-00), [ID3v2.3](https://id3.org/id3v2.3.0), [ID3v2.4 structure](https://id3.org/id3v2.4.0-structure), [ID3v2.4 frames](https://id3.org/id3v2.4.0-frames), [ID3v2.4 changes](https://id3.org/id3v2.4.0-changes).

## Field inventory and collisions

| Domain | ID3 storage and semantic boundary |
| --- | --- |
| Identification | TIT2 title, TIT3 subtitle, TALB album, TIT1 content group, TOAL original album, TOFN original filename. Title versions and remaster descriptions require distinct fields when they carry separate meaning. |
| Credits | TPE1 lead performer or artist, TPE2 band/orchestra/accompaniment, TPE3 conductor, TPE4 interpreter/remixer, TCOM composer, TEXT lyricist, TOPE original performer, TOLY original lyricist. Album artist in TPE2 is an established convention. An ordered artist list and a join-phrase display credit are distinct. |
| Production and performers | TIPL and TMCL are respectively role/person and instrument/person tuples in v2.4. IPLS (IPL in v2.2) is the earlier involved-people frame. Preserve tuple boundaries, role text, ordering, and unaffected pairs during updates. Picard conventions include producer, arranger, engineer, mix engineer, and DJ mixer roles. |
| Publishing | TPUB is specified as publisher. Picard conventionally uses it for record label. The registry must assign one unambiguous primary interpretation and allow separate simultaneous publisher and label values. TXXX:CATALOGNUMBER is an interoperability convention for catalog number. |
| Organization | TRCK and TPOS include a position and optional total separated by slash. Keep the components independently editable. Preserve the other component when updating one. TCMP is the iTunes compilation convention. |
| Classification | TCON genre, TBPM integer beats per minute, TKEY initial key in ID3 grammar, TLAN language, TMED media, TMOO mood in v2.4, TFLT file type, TOWN file owner. Store alternate key notation or fractional tempo where it can be preserved without truncation. |
| Date | TDRC recording, TDRL release, TDOR original release, TDEN encoding, TDTG tagging, TDLY playlist delay. Picard writes its release date to TDRC, or TYER plus TDAT on v2.3, as an interoperability convention. The same source date cannot be treated as independently populated recording and release dates. v2.3 TORY provides only the original release year. |
| Sorting | TSOT title sort, TSOP performer sort, TSOA album sort are v2.4 frames. TSO2 album artist sort and TSOC composer sort are iTunes conventions. |
| Rights and links | TCOP copyright message, WCOP copyright/legal information URL, OWNE ownership/purchase details, WPAY payment URL, WOAR official artist URL, WPUB publisher URL, WOAS audio source URL, WOAF audio file URL, WORS official station URL, WCOM commercial information URL, USER terms of use. Preserve independently identified URLs and relative URLs on read. A WXXX description can provide additional URL semantics. |
| Text and timing | COMM is identified by language and description. USLT stores unsynchronized lyrics. SYLT stores language, content type, description, timing units, and timed text. Its MPEG-frame timing option requires original frame timing context. ETCO contains structured event timing. Chapters use CHAP/CTOC with IDs, nested frames, ordered and hierarchical tables of contents, and potentially absolute file offsets. Increasing the leading tag size shifts audio offsets and can invalidate CHAP offsets or other locator metadata. |
| Pictures | APIC stores original bytes or an external link, MIME, picture type, and description. PIC uses a format marker. Preserve untouched encoded bytes and the identity of each image. Multiple roles and descriptions must survive an unrelated edit. |
| Playback | POPM stores a rater identity, an unsigned rating byte, and a variable-width count. PCNT is a separate variable-width play counter. Keep absent and zero distinct and retain the rater identity and original width where necessary. RVA2 is channel-specific relative volume adjustment and optional peak data. Gapless encoder delay/padding and Sound Check require their own semantics. |
| Classical and podcast | Picard accepts TXXX:WORK or TIT1 for work. Keep work and ordinary grouping distinct. MVNM and MVIN are iTunes movement conventions. Podcast conventions such as PCST, TCAT, TDES, TGID, TKWD, and WFED require implementation evidence before being advertised. MP4 native chapter tracks and ID3 chapter tables can carry richer structures than simple timestamp/title lists. |
| Binary | UFID stores an owner identifier and up to 64 binary bytes in v2.4. GEOB carries MIME, filename, description, and object data. PRIV is owner-specific opaque bytes. Unknown payloads, ownership/signature frames, and format flags require raw preservation. |

Sources for this inventory are the [ID3v2.3 frame specifications](https://id3.org/id3v2.3.0), [ID3v2.4 frame specifications](https://id3.org/id3v2.4.0-frames), [ID3 Chapter Frame Addendum](https://id3.org/id3v2-chapters-1.0), [ID3 developer convention notes](https://id3.org/Developer%20Information), and [Picard tag mapping](https://picard-docs.musicbrainz.org/en/v2.13/appendices/tag_mapping.html). [Mutagen's ID3 notes](https://mutagen.readthedocs.io/en/latest/user/id3.html) illustrate the compatibility limitations of v2.3 multi-value writes. [TagLib's property mapping](https://taglib.org/api/p_propertymapping.html) supplies a separate interoperability reference.

## Identifiers

Keep identifiers as text when their presented representation matters, including leading zeros and fixed width. Preserve unknown identifiers by owner and bytes. Validate only the syntax that the field promises, and keep the original raw form if an imported value is malformed. A syntactically valid identifier may still be unassigned.

| Semantic field | Recommended storage or distinction |
| --- | --- |
| ISRC | ID3 TSRC, v2.2 TRC, Vorbis/FLAC/Opus ISRC, Picard MP4 freeform ISRC in com.apple.iTunes. Normalize well-formed display separators and case for authored values. Compact syntax has two letters, three alphanumeric characters, and seven digits. The reference year describes assignment and cannot supply the recording year. |
| UPC, EAN, GTIN, or barcode | Represent as text and keep leading zeros. For a specifically typed GTIN, validate its allowed GS1 length and check digit. A general legacy BARCODE field can preserve other serializations without interpreting them as GTINs. Picard conventionally uses TXXX:BARCODE, BARCODE, and com.apple.iTunes BARCODE freeform. |
| ISWC | Identifies a musical work. Keep it distinct from recording ISRC, artist IDs, and release identifiers. |
| MusicBrainz recording ID | Conventional UFID owner http://musicbrainz.org, Vorbis MUSICBRAINZ_TRACKID, and MP4 freeform MusicBrainz Track Id. The historical track wording refers to a recording in these storage names. |
| MusicBrainz release track ID | Conventional TXXX:MusicBrainz Release Track Id, MUSICBRAINZ_RELEASETRACKID, and corresponding Apple freeform name. Keep separate from recording ID. |
| Other MusicBrainz IDs | Keep artist, album artist, release, release group, work, original artist, and original release separate. Artist lists may have multiple UUIDs. Preserve their ordering without inferring alignment with separate display values. Preserve discontinued TRM and PUID identifiers when encountered. |
| AcoustID and Chromaprint | AcoustID is a UUID identifying a cluster in the AcoustID service. A Chromaprint fingerprint is a separate encoded payload, with its algorithm/version implicit in the format. Picard uses TXXX:Acoustid Id and TXXX:Acoustid Fingerprint, ACOUSTID_ID and ACOUSTID_FINGERPRINT, and matching Apple freeform descriptors. |
| Retailer and catalog IDs | ASIN, label catalog number, and iTunes catalog identifiers are different from GS1 and MusicBrainz IDs. Confirm the store and identifier scope when assigning an alias. |
| CD identifiers and extraction metadata | A MusicBrainz Disc ID is derived from CD track offsets. Keep it separate from a FLAC CUESHEET, an ID3 MCDI TOC, and external EAC log/cue artifacts. Editing a semantic ID must leave those technical structures intact. |

Sources include [IFPI ISRC structure](https://isrc.ifpi.org/isrc-standard/isrc-structure), [GS1 GTIN and UPC distinctions](https://support.gs1.org/support/solutions/articles/43000734124-what-is-the-difference-between-a-gs1-gtin-a-barcode-an-ean-and-a-upc-), [CISAC identifier standards](https://www.cisac.org/services/information-services/international-identifiers), [MusicBrainz identifier definition](https://musicbrainz.org/doc/MusicBrainz_Identifier), [MusicBrainz Disc ID](https://musicbrainz.org/doc/Disc_ID), [AcoustID service protocol](https://acoustid.org/webservice), and [Picard tag mapping](https://picard-docs.musicbrainz.org/en/v2.13/appendices/tag_mapping.html).

## Audio analysis

- ReplayGain gain and peak each have a track and an album value. Gains are in dB and peaks are ratios relative to full scale. True peaks may exceed 1. Keep finite decimal values and reject nonfinite values rather than serializing them. Keep reference loudness and loudness range independent. Conventional names are REPLAYGAIN_TRACK_GAIN, REPLAYGAIN_TRACK_PEAK, REPLAYGAIN_ALBUM_GAIN, and REPLAYGAIN_ALBUM_PEAK. Picard uses the names in ID3 TXXX, Vorbis comments, and MP4 freeform atoms under com.apple.iTunes. [ReplayGain revised specification](https://wiki.hydrogenaudio.org/index.php?title=ReplayGain_2.0_specification), [Picard tag mapping](https://picard-docs.musicbrainz.org/en/v2.13/appendices/tag_mapping.html).
- Ogg Opus defines one R128_TRACK_GAIN and one R128_ALBUM_GAIN at most. These tags are signed decimal encodings of Q7.8 dB gain, relative to the Opus ID header's output gain and a -23 LUFS reference. Preserve the existing header output gain and label its meaning separately. The RFC discourages ReplayGain comments for Opus except where used in a different context. Use a distinct AudioMeta representation when transferring ordinary ReplayGain into Opus and retain unknown legacy comment values. [RFC 7845 section 5.2.1](https://www.rfc-editor.org/rfc/rfc7845.html#section-5.2.1).
- Song/album loudness, ReplayGain, Opus R128, arbitrary ID3 RVA2 gain, and Apple Sound Check have different conventions and potentially different reference levels or quantization. Do not infer one from the other and do not rewrite encoded audio gain, delay, or padding. If a future adapter offers conversion, require an explicit reference and represent any conversion loss. [ID3v2.4 native frames](https://id3.org/id3v2.4.0-frames), [ID3 developer convention notes](https://id3.org/Developer%20Information), [RFC 7845 section 5.1](https://www.rfc-editor.org/rfc/rfc7845.html#section-5.1).

## Rewrite and verification policy

An ordered ID3 frame editor needs frame-header fidelity as well as payload fidelity. ID3v2.3 and v2.4 flags govern tag/file-alter preservation, read-only status, and optional compression, grouping, encryption, or unsynchronization details. If a flag requires dropping an unknown frame on edit, an edit that guarantees preservation should fail explicitly. Editing a signature-related or read-only frame also requires explicit handling. An ordinary tag edit preserves the MPEG stream and trailer bytes unless it explicitly targets trailer metadata. [ID3v2.3 format](https://id3.org/id3v2.3.0), [ID3v2.4 structure](https://id3.org/id3v2.4.0-structure).

Native and conventional fixture assertions should inspect frames or atoms independently with Mutagen, TagLib, ExifTool, or FFprobe as appropriate. Audio integrity verification should also compare the original audio suffix where the tag boundary is known and confirm sample decoding with FFmpeg. An implementation relying on private fallback encodings needs round-trip evidence of the typed values and preservation of unrelated native data. The resulting capability matrix reports the tested adapter behavior for each version.
