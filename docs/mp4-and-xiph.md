# MP4, FLAC, Vorbis, and Opus metadata research

This report records representation choices and compatibility constraints for the AudioMeta registry. Format support is established by adapter and independent-tool tests. Recommendations below identify storage candidates and their provenance.

## MP4, M4A, and M4B

ISO/IEC 14496-12 defines the ISO Base Media File Format box structure and mechanisms for timed and item metadata. The ISO public preview covers informative material and the catalog identifies the current 2026 edition. The MP4 Registration Authority lists the provenance of registered box types, including `cprt` in ISO user data. An iTunes `ilst/cprt/data` entry and an ISO user-data `cprt` box have different payload structures. [ISO/IEC 14496-12:2026 preview](https://www.iso.org/obp/ui?_escaped_fragment_=iso%3Astd%3Aiso-iec%3A14496-12%3Aed-8%3Av1%3Aen) · [IEC edition history](https://webstore.iec.ch/en/publication/113218) · [MP4 Registration Authority](https://mp4ra.org/registered-types/boxes)

Apple documents the QuickTime keyed metadata mechanism, which uses `meta/hdlr`, `keys`, and indexed `ilst` items with typed and optionally localized `data`. Movie, track, and media metadata scopes each have their own meaning. Apple also documents iTunes and QuickTime metadata as separate collections in AVFoundation. The widely used iTunes audio layout is `moov/udta/meta` with manager handler `mdir` and four-byte item codes under `ilst`. Registry rows should identify which convention and box path they mean. [Apple QuickTime metadata atoms](https://developer.apple.com/documentation/quicktime-file-format/metadata_atoms_and_types) · [Apple AVFoundation metadata collections](https://developer.apple.com/documentation/avfoundation/retrieving-media-metadata) · [Apple iTunes metadata identifiers](https://developer.apple.com/documentation/avfoundation/avmetadataidentifier#iTunes-metadata-identifiers) · [Mutagen MP4 encoder](https://github.com/quodlibet/mutagen/blob/main/mutagen/mp4/__init__.py)

An iTunes freeform item is a `----` child under `ilst`, with `mean` namespace and `name` identifier children, followed by one or more typed `data` children. `mean` and `name` each have a four-byte version/flags prefix. Each `data` child has type/version and locale words followed by the payload. Use the convention's exact identifier and case when third-party software supplies an established name. Preserve byte-for-byte unknown items, including vendor-specific types, locales, sub-boxes, and repeated values. AudioMeta uses `io.github.gcottom.audiometa` as its iTunes `mean` and the names `audiometa/1/<id>` and `audiometa/1/custom/<key>`. [AtomicParsley iTunes layout and freeform notes](https://atomicparsley.sourceforge.net/mpeg-4files.html) · [Mutagen MP4 metadata](https://mutagen.readthedocs.io/en/latest/api/mp4.html) · [TagLib MP4 editor](https://github.com/taglib/taglib/blob/master/taglib/mp4/mp4tag.cpp)

| --- | --- |
| Basic text | `©nam`, `©alb`, `©ART`, `aART`, `©wrt`, `©grp`, `©cmt`, `©gen`, `©lyr`, `©too`, and iTunes `cprt`. Each © in this report represents one byte, 0xA9. Legacy `gnre` is 1-based ID3v1 genre and is a read alias only when its semantics are unambiguous. |
| Dates | `©day` represents the tagged release date in Picard practice. TagLib uses freeform `ORIGINALDATE` and `RELEASEDATE` for corresponding mapped properties. Keep recording and original release time distinct and retain partial strings. |
| Indexes | `trkn` and `disk` contain uint16 number and total in the same payload. Preserve the other member when editing one. Resolve unknown versus numeric zero explicitly. |
| Organization | `cpil` compilation flag, `tmpo` integer BPM, and `stik` iTunes media kind. Separate medium (CD, digital media) from iTunes content kind. `rtng` represents content advisory. |
| Sorting | `sonm`, `soar`, `soal`, `soaa`, and `soco` for title, artist, album, album artist, and composer; `sosn` for show. |
| Classical | `©wrk` work, `©mvn` movement name, `©mvi` movement index, `©mvc` movement count, and `shwm` show work/movement. |
| Podcast and video | `pcst`, `catg`, `egid`, `purl`, `keyw`, `desc`, and `ldes` have established podcast uses, with documented tool variation for short/long descriptions. `tvsh`, `tves`, `tvsn`, `tven`, and `tvnn` have television semantics; any overlap with podcast episode or season needs a stated compatibility rule. |
| Identifiers and production | Existing `com.apple.iTunes` names include `ISRC`, `BARCODE`, `CATALOGNUMBER`, `ASIN`, `LABEL`, `PRODUCER`, MusicBrainz and AcoustID identifiers, and the ReplayGain family. Compare Picard and TagLib before deciding each exact spelling and aliases. |
| Playback | `pgap` describes membership in a gapless album. Encoder delay/padding in `iTunSMPB` and playback edits are technical information with read-only semantics. Personal ratings need a separate representation. |
| Artwork | `covr` supports multiple JPEG or PNG encoded payloads. Artwork role, description, URI, and some additional image formats require lossless extension data. Distinguish unknown role from an explicitly tagged front cover. |

QuickTime chapters are named samples in a text track referenced with `chap`. Nero `moov/udta/chpl` is another implemented chapter convention. QuickTime timed metadata has tracks, sample formats and references. Their carriage affects structure and offset tables. Retain existing tables and tracks when editing tags. A lossless independent AudioMeta chapter or synchronized lyric value can retain timing, language, speaker and end times without promising player recognition. A native chapter implementation must account for files with both schemes and avoid creating contradictory visible chapters. [Apple QuickTime chapter lists](https://developer.apple.com/documentation/quicktime-file-format/chapter_lists) · [Apple QuickTime media data types](https://developer.apple.com/documentation/quicktime-file-format/media_data_atom_types) · [FFmpeg MP4 options](https://ffmpeg.org/ffmpeg-formats.html#mov_002c-mp4_002c-ismv)

### MP4 preservation constraints

- Edit only the intended movie-scope iTunes metadata collection. Keep keyed `mdta`, track-level data, unknown `uuid` and sibling boxes, the original item ordering, and existing artwork encodings.
- Chunk offset updates must account for the actual relocated media ranges and both `stco` and `co64` tables. Fragmented files can also have `tfhd`, `sidx`, and other offset relationships. Unsupported layouts require a preflight error if their integrity cannot be guaranteed. Metadata edits must leave codec configuration, protection information, and media bytes intact.
- Use raw box lengths including extended-size and size-to-end encodings and validate parent boundaries before reading. iTunes text may use different encodings or locales. Keep malformed and unsupported items as opaque, or explicitly reject if a safe edit cannot be proven.
- Cross-check emitted known atoms with Mutagen or TagLib and report where independent tools only consume the first of multiple values. Verify duration and decoded samples with FFmpeg. Check payload bytes in `mdat` as a separate preservation assertion.

## Xiph Vorbis comments

The official Vorbis comment packet has a vendor vector and an ordered list of length-prefixed UTF-8 `NAME=value` vectors with a mandatory framing bit. Keys are case-insensitive printable ASCII from U+0020 through U+007D excluding `=`, per the Vorbis specification. Repeated keys are permitted and useful for ordered multi-value data. Values can contain `=` and can be explicitly empty. A parsed sequence with raw spelling is more faithful than a map for read, preserve and save. Splitting at the first `=` preserves a URL query or description containing an equals sign. [Xiph Vorbis I specification §5](https://xiph.org/vorbis/doc/Vorbis_I_spec.html#x1-790005) · [Xiph Vorbis comment field specification](https://xiph.org/vorbis/doc/v-comment.html)

The Xiph vocabulary recommends `TITLE`, `VERSION`, `ALBUM`, `TRACKNUMBER`, `ARTIST`, `PERFORMER`, `COPYRIGHT`, `LICENSE`, `ORGANIZATION`, `DESCRIPTION`, `GENRE`, `DATE`, `LOCATION`, `CONTACT`, and `ISRC`. The registry should recognize their documented semantics. Xiph `DATE` refers to recording, while Picard writes its release date there. Projects needing both should select an explicit primary mapping and keep the other using a separate key. The legacy date should be interpretable with the chosen policy, and a single ambiguous raw value should not be read as independent recording and release events. Similarly, `ARTIST` repeats can represent multiple artists, while Picard distinguishes a display credit (`ARTIST`) from individual credits (`ARTISTS`). Read opaque or ambiguous values without inventing identity boundaries. [Xiph Vorbis comment field specification](https://xiph.org/vorbis/doc/v-comment.html) · [Picard mappings](https://picard-docs.musicbrainz.org/en/latest/appendices/tag_mapping.html)

| Semantic area | Established comment usage and caveats |
| --- | --- |
| Credits | `ALBUMARTIST` / `ALBUMARTISTS`, `COMPOSER`, `LYRICIST`, `CONDUCTOR`, `ARRANGER`, `PRODUCER`, `ENGINEER`, `MIXER`, `REMIXER`. Picard writes `PERFORMER=Artist (instrument)`, a convention with ambiguity when names contain parentheses. |
| Organization | `TRACKNUMBER`, `TRACKTOTAL`, `DISCNUMBER`, `DISCTOTAL`; recognize `TOTALTRACKS` / `TOTALDISCS` where present. A slash pair is another read convention. `COMPILATION`, `BPM`, `MOOD`, `KEY` or `INITIALKEY` need exact names and aliases per independent tools. |
| Publishing and dates | `ORGANIZATION` is Xiph record-label practice, `LABEL` is Picard practice, and `PUBLISHER` can carry a separate publishing role. `ORIGINALDATE` retains partial original release dates; `ORIGINALYEAR` has lower precision. |
| Identifiers | `ISRC`, `BARCODE`, `CATALOGNUMBER`, `ASIN`, `ACOUSTID_ID`, `ACOUSTID_FINGERPRINT`, and `MUSICBRAINZ_*`. Keep Picard's recording (`MUSICBRAINZ_TRACKID`) and release-track (`MUSICBRAINZ_RELEASETRACKID`) IDs distinct. |
| Sorting and classical | `TITLESORT`, `ARTISTSORT`, `ALBUMSORT`, `ALBUMARTISTSORT`, `COMPOSERSORT`, `WORK`, `MOVEMENTNAME`, `MOVEMENT` and `MOVEMENTTOTAL`. |
| Text and websites | `COMMENT`, `DESCRIPTION`, `LYRICS`, `LANGUAGE`, `WEBSITE`. Preserve distinctions between general contact info and a typed link, and between lyric text and a timestamped transcript. |

[Picard tag mapping and version notes](https://picard-docs.musicbrainz.org/en/latest/appendices/tag_mapping.html) · [TagLib properties](https://taglib.org/api/p_propertymapping.html) · [Xiph community comments](https://wiki.xiph.org/VorbisComment)

For Ogg artwork, Xiph documents `METADATA_BLOCK_PICTURE` as the base64 encoding of the FLAC PICTURE body, with multiple pictures via repeated keys. Preserve unknown picture types and header details when possible. Existing `COVERART` and `COVERARTMIME` may be recognized with a documented legacy policy. The Xiph chapter extension uses indexed `CHAPTERxxx` and `CHAPTERxxxNAME` keys. It supports start time and title. Exact end times, URLs, subchapters, and other structured values need an explicit extension or an unsupported-operation error. [Xiph picture convention](https://wiki.xiph.org/VorbisComment) · [Xiph chapter convention](https://wiki.xiph.org/Chapter_Extension)

## Ogg Opus

RFC 7845 defines `OpusTags` as the second packet. It has Vorbis-style lengths, vendor and comments, without the Vorbis framing bit. Preserve any trailer after the comment list, especially when bit 0 of its first byte is set. The second header must finish its page; growth may require multiple pages. Validate counts and lengths against the bytes actually present before allocating, and enforce bounded allocations. [RFC 7845 §§3, 5.2](https://datatracker.ietf.org/doc/html/rfc7845#section-5.2)

`R128_TRACK_GAIN` and `R128_ALBUM_GAIN` are optional standardized signed decimal integers in the range −32768 through 32767, in units of 1/256 dB. They describe normalization relative to the OpusHead output gain. Writers should avoid emitting `REPLAYGAIN_*` as active Opus normalization tags because RFC 7845 warns about competing interpretations. Preserve existing ReplayGain as a recognized alias or store a transferred ReplayGain value separately in lossless extension storage. R128, ReplayGain and encoder output gain carry different semantics. OpusHead data including gain and pre-skip, Ogg granule and end-trim semantics, and audio packet bytes should survive metadata edits. [RFC 7845 §§4, 5.1, 5.2.1](https://datatracker.ietf.org/doc/html/rfc7845#section-5.2.1) · [Picard ReplayGain mappings](https://picard-docs.musicbrainz.org/en/latest/appendices/tag_mapping.html)

Ogg pages are CRC-protected, numbered per stream, and may contain continuations or several packet boundaries. Exact multiples of 255 bytes still require a terminating lacing segment. For tag changes that grow or shrink page count, preserve granule positions on audio pages, rebuild changed pages and subsequent sequence numbers for the selected logical stream, and keep other serials or chained links untouched. Reject a chain or multiplexing layout when the selection and preservation behavior is undefined. Vorbis identification, setup and audio packets and Opus identification and audio packets are independent integrity check inputs. [RFC 3533 §§4, 6](https://datatracker.ietf.org/doc/html/rfc3533#section-6) · [Vorbis in Ogg mapping](https://xiph.org/vorbis/doc/Vorbis_I_spec.html) · [RFC 7845 §3](https://datatracker.ietf.org/doc/html/rfc7845#section-3)

## FLAC

RFC 9639 documents native FLAC metadata blocks and tag vocabulary. Its `VORBIS_COMMENT` block has no Ogg signature or framing bit, permits at most one block, and carries length-prefixed UTF-8 strings. FLAC allows the printable ASCII range through U+007E except `=` for the field name. Common interchange keys should use the shared comment range. The RFC formally defines only the technical channel-mask key; Title, Artist and Album and other semantic keys use established conventions. The channel mask should be reserved from custom edits and metadata clearing. [RFC 9639 §§8.1, 8.6](https://datatracker.ietf.org/doc/html/rfc9639#section-8.6)

Native `PICTURE` blocks support multiple entries, image data or URI, media type, picture role, UTF-8 description, width, height, color depth, and palette count. Every metadata block, including each picture and the entire comment block, has a 24-bit payload length and thus a maximum of 16,777,215 bytes. Reject oversized writes before output. Keep media bytes and the declared properties independent of how an image decoder presents them. [RFC 9639 §§8.1, 8.8](https://datatracker.ietf.org/doc/html/rfc9639#section-8.8)

`CUESHEET` stores sample-relative tracks and indexes for disc layouts and may include catalog and per-track ISRC data. A sample-accurate disc cue sheet and a generic list of named chapters represent different structures. Treat the cue sheet and playback technical properties as independent read-only data until editing can preserve their restrictions. Preserve STREAMINFO, SEEKTABLE, APPLICATION, and reserved blocks as ordered raw metadata. Audio-frame copying can use their source ranges and does not require decoding. [RFC 9639 §§8.1–8.7](https://datatracker.ietf.org/doc/html/rfc9639#section-8) · [Xiph FLAC command-line tools](https://github.com/xiph/flac/blob/master/man/flac.md)

## Registry and verification implications

- Classify the semantic representation, with separate evidence for its storage carrier. FLAC PICTURE and RFC 7845 gain tags have standardized semantics. The official Xiph Vorbis recommendations and Picard's additional keys need their provenance noted. Apple iTunes atoms and freeform fields are conventions in this matrix.
- Keep file creation time, channel layout, technical gain, seek and edit tables, playback trim, and protected media separate from editable descriptive metadata. Add release country, status and type, original filename, album and artist IDs, Apple Store IDs, podcast keywords, and the disc layout review to the field inventory.
- Read primary fields before their aliases and AudioMeta extensions. Preserve source conflicts and opaque values on unrelated edits. On targeted removal, document which attached aliases and physical items are removed and retain technical tags even during a descriptive metadata clear.
- Avoid inferring that an independent parser's success verifies every value. Read emitted ordered text and encoded artwork with Mutagen/TagLib or `metaflac`, inspect MP4 atom structure with AtomicParsley when available, and check FFmpeg decode, durations, configuration and compressed payload preservation separately. Include damaged lengths, duplicate keys, explicit empties, multi-page tag growth, mixed-case keys, unknown picture roles, localized and freeform MP4 children, and files with multiple metadata scopes among the fixtures.
